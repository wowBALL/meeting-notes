# tools/

เครื่องมือที่รันด้วยมือ ไม่ใช่ส่วนหนึ่งของ pipeline -- ไม่มีอะไรใน `src/` import ของในนี้

## calibrate_voiceprints.py

วัดว่าคะแนนของ "คนเดียวกัน" กับ "คนละคน" แยกกันจริงหรือไม่ในพื้นที่เวกเตอร์ที่
`EMBEDDING_MODEL` ปัจจุบันสร้าง แล้วเสนอค่า `SPEAKER_MATCH_HIGH`/`SPEAKER_MATCH_LOW`
ที่อยู่ในช่องว่างระหว่างสองกอง

รันใหม่เมื่อไหร่: เปลี่ยน `EMBEDDING_MODEL`, เปลี่ยนวิธีคัดช่วงเสียงใน `src/voiceprint.py`
หรือเมื่ออยากรู้ว่าเกณฑ์ที่ตั้งอยู่ยังมีหลักฐานรองรับอยู่ไหม -- ค่าคู่นั้นตัดสินว่าจะใส่
ชื่อใครลง `transcript.md` โดยไม่ถามใคร มันจึงต้องมาจากการวัด ไม่ใช่การเดา

### ไฟล์เฉลย

บอกว่าป้าย `SPEAKER_xx` ในไฟล์ไหนคือใคร:

```json
[{"audio": "meetings/2026-01-02_09-00-Standup/Standup-09-00-00.ogg",
  "truth": {"SPEAKER_05": "somchai", "SPEAKER_02": "malee"}},
 {"audio": "enroll/done/somchai.ogg", "truth": {"*": "somchai"}}]
```

- `audio` เป็น path เทียบกับรากโปรเจกต์ (หรือ path สัมบูรณ์) -- นามสกุลอะไรก็ได้ที่
  ffmpeg อ่านออก ไฟล์ถูกแปลงเป็น wav 16k โมโนก่อนเสมอ แบบเดียวกับที่ระบบจริงทำ
- `"*"` = ทุกป้ายในไฟล์นี้เป็นคนเดียวกัน สำหรับคลิป enroll ที่พูดคนเดียว -- ใช้แทนการ
  ไล่เขียนทีละป้าย เพราะ pyannote แยกคลิปพูดคนเดียวออกเป็นสองป้ายได้บ่อย
- **ป้ายที่ไม่อยู่ในเฉลยถูกข้าม ไม่ถูกเดาว่าเป็นใคร** -- อย่าเขียนเฉลยของป้ายที่ยังไม่แน่ใจ
  การเดาว่า "ป้ายที่เหลือคือคนอื่นทั้งหมด" จะทำให้คู่ที่จริง ๆ เป็นคนเดียวกัน (แต่ pyannote
  แยกเป็นสองป้าย) ถูกนับเป็นคู่คนละคน แล้วดันเพดานของกองคนละคนขึ้นไปเอง เกณฑ์ที่ได้จะ
  เข้มเกินจริงแล้วปฏิเสธคนที่ถูกต้อง
- ชื่อคนเป็นแค่ป้ายสำหรับจับคู่ ใช้ชื่อเล่นหรือรหัสก็ได้ ขอแค่คนเดียวกันใช้สตริงเดียวกัน
  ทุกไฟล์

ไฟล์เฉลยของจริงมีชื่อคนจริง **จึงไม่เข้า repo** -- `speakers-truth.json` อยู่ใน
`.gitignore` แล้ว เหมือน `teams.md` และ `glossary.md`

### ⚠ เลข `SPEAKER_xx` ไม่ใช่ชื่อถาวรของคน

มันคือหมายเลขที่ pyannote แจกใหม่ทุกครั้งที่ diarize **เฉลยจึงผูกกับผลการ diarize ครั้งนั้น
ครั้งเดียว ไม่ได้ผูกกับไฟล์เสียง** ตราบใดที่ `--cache` ยังอยู่ turns ชุดเดิมถูกใช้ซ้ำ เลข
ป้ายจึงนิ่ง -- ลบแคชทิ้ง (หรือเปลี่ยน `DIARIZATION_MODEL` หรือเปลี่ยนวิธีเตรียมเสียง) แล้ว
เลขจะเลื่อนทั้งชุด และเฉลยเดิมจะจับคู่ผิดคนโดยไม่มีอะไรฟ้อง -- คะแนนที่ได้จะดู "ต่ำจนน่า
สงสัย" แทนที่จะ error

เกิดขึ้นจริง 2026-07-31: การวัดรอบแรกป้อน `.ogg` 48 kHz เข้า pyannote ตรง ๆ ส่วนรอบที่สอง
แปลงเป็น wav 16 kHz ก่อน (ทางที่ระบบใช้จริง) ไฟล์เดียวกัน โมเดลเดียวกัน แต่ได้ 2143 กับ
2248 ท่อน คนละชุดกัน คนที่เคยเป็น `SPEAKER_05` กลายเป็น `SPEAKER_03` แล้วคะแนนของคู่ที่
ถูกต้องอ่านได้ 0.3451 แทนที่จะเป็น 0.6679

**ถ้าคะแนนของคู่ที่ควรจะสูง ออกมาต่ำผิดปกติ ให้สงสัยเลขป้ายก่อนสงสัยโมเดล** รันด้วย
`--extract-clips` แล้วฟังยืนยันใหม่ ไม่ใช่แก้เกณฑ์ให้ผ่าน

### คู่ไหนถูกนับ

สองกองรับคู่คนละชุด และความไม่สมมาตรนี้ตั้งใจ -- แต่ละกองรับค่าจากฝั่งที่อนุรักษ์นิยม
ที่สุดของตัวเอง:

| กอง | รับคู่ | เพราะ |
|---|---|---|
| คนเดียวกัน (เป็น *พื้น*) | ข้ามไฟล์เท่านั้น | คู่ในไฟล์เดียวกันใช้ไมค์/ห้อง/codec เดียวกัน คะแนนสูงกว่าความจริง 0.05-0.15 เอามาเป็นพื้นจะได้เกณฑ์เข้มเกินจริงแล้วปฏิเสธคนที่ถูกต้อง |
| คนละคน (เป็น *เพดาน*) | ทุกคู่ รวมในไฟล์เดียวกัน | คู่คนละคนในประชุมเดียวกันคือรูปทรงของการใส่ชื่อผิดที่เกิดจริง และทำคะแนนสูงกว่าคู่ข้ามการบันทึกมาก (0.6313 เทียบกับ 0.4310) เวอร์ชันแรกตัดทิ้ง จึงเสนอ HIGH 0.59 ซึ่งอยู่ใต้คะแนนที่คนละคนทำได้จริง |

### วิธีรัน

```bash
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe -m tools.calibrate_voiceprints \
  speakers-truth.json --cache .calib-cache --extract-clips .calib-clips
```

- `--cache DIR` **ควรใส่เสมอ**: ไฟล์ประชุมเต็มใช้เวลาแยกผู้พูดหลายนาที การเก็บ turns ไว้
  ทำให้ปรับวิธีคิดคะแนนแล้วรันซ้ำได้ในไม่กี่วินาที แคชผูกกับไบต์ของไฟล์และชื่อโมเดล
  แยกผู้พูด สลับ `DIARIZATION_MODEL` แล้วมันจะ diarize ใหม่ให้เอง ไม่เสิร์ฟของเก่าให้
- `--extract-clips DIR` เขียนเสียงท่อนที่ยาวที่สุดของแต่ละป้าย (ตัดที่ 12 วินาที) ไว้ฟัง
  -- นี่คือขั้นที่ทำให้เขียนไฟล์เฉลยได้ตั้งแต่แรก รันครั้งแรกด้วยเฉลยว่าง ๆ (`{}`) เพื่อ
  เอาคลิปมาฟังก่อน แล้วค่อยเติมว่าป้ายไหนเป็นใคร
- ทั้งสองโฟลเดอร์อยู่ใน `.gitignore` แล้ว (มีเสียงคนจริงกับผลที่ผูกกับมัน)

exit code `0` = สองกองแยกกัน, `1` = ซ้อนกัน (หรือไม่มีคู่ให้วัดเลย) ตอนซ้อนกันสคริปต์จะ
**ไม่เสนอเลขให้** โดยเจตนา -- ให้ไปดูตารางคะแนนรายคู่ว่าคู่ไหนทำให้ซ้อน ซึ่งเกือบทุกครั้ง
คือเฉลยที่ผิดหนึ่งบรรทัด หรือป้ายที่ pyannote ปนเสียงสองคนไว้ในป้ายเดียว

## check_glossary.py

ตรวจ `glossary.md` หาคำผิดที่จะไปกินคำอื่น และวัดว่าคำผิดตัวไหนเคยโผล่ในประชุมจริงบ้าง

```bash
python -m tools.check_glossary            # รายงานปกติ
python -m tools.check_glossary --show-dead # รวมคำที่ไม่เคยโผล่เลย
```

รันเมื่อไหร่: **ทุกครั้งก่อนแก้ `glossary.md`** และเป็นระยะเพื่อดูว่าคำไหนตายแล้ว

ทำไมต้องมี: `## exact` แทนที่แบบ substring ล้วนและแทนที่ **ก่อน** โมเดลเห็น transcript
เมื่อมันแก้ผิด ไม่มีใครในสายงานที่เหลือรู้ได้เลยว่าเดิมพูดว่าอะไร -- ทั้งโมเดลและคนอ่านสรุป
ความผิดพลาดชั้นนี้จึงเงียบสนิทโดยธรรมชาติ สองเคสที่เจอมาแล้วกับประชุมจริง (2026-08-01)
ถูกเจอโดยบังเอิญระหว่างไล่เรื่องอื่นทั้งคู่:

- `Engage` เป็นคำผิดของ `Ingress` -- คนพูดว่า "มันจะ Engage ให้ได้ไหม" ถามว่าเครื่องมือ
  จะจัดไฟล์ให้เองได้ไหม โมเดลได้รับ "มันจะ Ingress ให้ได้ไหม" ซึ่งไม่มีความหมาย
- ถอด `Control Panel` ออกจากคำผิดของ `Control Plane` แล้วยังไม่พอ เพราะ `Control Pane`
  ที่เหลือไว้กิน "Control Panel" ไปครึ่งเดียวจนได้ "Control Planel"

### อ่านผลยังไง

| ระดับ | หมายความว่า |
|---|---|
| `✗ หนัก` | คำผิดอยู่ข้างในคำถูกตัวใดตัวหนึ่ง -- ใครพูดคำถูกนั้นออกมาถูกอยู่แล้วจะโดนแก้ให้เพี้ยน แก้ก่อนสรุปประชุมถัดไป (exit code 1) |
| `! เบา` | คำผิดสั้นกว่า 4 อักขระ, ชี้ไปหาตัวเอง, หรือถูกคำผิดตัวยาวกว่าคลุมอยู่ -- ดูเอาว่าตั้งใจหรือเปล่า |

ส่วน "วัดกับ transcript จริง" นับจากไฟล์ดิบใน `meetings/*/transcript.md` (ตัวกรองไม่แตะ
ไฟล์นั้น) ตัวเลขนี้ใช้ได้สองทาง -- **ยืนยัน** ว่าคำผิดที่เดาไว้เจอของจริง (เช่น `Payload`
21 ครั้ง ทุกครั้งหมายถึง Payroll จริง) และ **หาของที่ตายแล้ว** ที่ยังกิน token อยู่ทุกครั้ง
ที่สรุปถ้ามันอยู่ในชั้น `fuzzy`

`fuzzy` กับ `project-names` ไม่ถูกตรวจเรื่องคำกินกัน โดยเจตนา: สองชั้นนั้นโมเดลเป็นคน
ตีความตามบริบท คำที่มีความหมายของตัวเองจึงปลอดภัยเมื่ออยู่ที่นั่น -- นั่นคือเหตุผลทั้งหมด
ที่ชั้นนั้นมีอยู่ และเป็นที่ที่ควรย้ายคำไปเมื่อตัวตรวจเตือน
